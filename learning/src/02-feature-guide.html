F1Google sign-in

One click "Continue with Google". The browser gets a signed token from Google (via Firebase), our server checks that token, and then gives the browser our own session cookie.

Why it is built this way

The browser could just send "my email is x@gmail.com" — but anyone can send that. A Firebase ID token is signed by Google. Our server verifies the signature with Firebase Admin, so the email inside is trustworthy. After that we stop using Firebase and issue our own JWT, so the rest of the app doesn't care how you logged in.

The code

export const loginWithGoogle = async (idToken) => {
    let decoded;
    try {
        decoded = await firebaseAuth.verifyIdToken(idToken);
    } catch {
        throw new AppError(401, "Invalid Google token");
    }
    if (!decoded.email || !decoded.email_verified) {
        throw new AppError(401, "Google account email not verified");
    }
    return findOrCreateGoogleUser({
        email: decoded.email.toLowerCase(),
        name: decoded.name || decoded.email.split("@")[0],
    });
};

The important code

server/src/modules/auth/auth.service.js 
const BCRYPT_ROUNDS = 12; // ~0.2 s per hash — fine for a user, very slow for an attacker
const DUMMY_HASH = bcrypt.hashSync("dummy-password-for-timing", BCRYPT_ROUNDS);
const hashToken = (token) => crypto.createHash("sha256").update(token).digest("hex");

export const loginWithPassword = async ({ email, password }) => {
    const user = await User.findOne({ email }).select("+password");
    // no user? still run a compare, so the response time doesn't reveal it
    const isMatch = await bcrypt.compare(password, user?.password || DUMMY_HASH);
    if (!user || !user.password || !isMatch) throw new AppError(401, "Invalid email or password");
    // only AFTER the right password do we reveal "not verified"
    if (!user.isVerified) throw new AppError(403, "Please verify your email first...", "EMAIL_NOT_VERIFIED");
    return toSafeUser(user);
};

Security ideas in this feature

Hash the link token

The email contains the plain token; the DB stores only its SHA-256. If the database leaks, nobody can build a working link. SHA-256 (fast) is fine here because the token is 256 random bits — impossible to guess, unlike a password.

No account enumeration

Same message for unknown email and wrong password; dummy bcrypt compare; forgot-password always answers "if an account exists…" and sends the email without await (SMTP takes ~1 s — waiting only for real users would leak by timing).

Single use + expiry

Verify links last 24 h, reset links 1 h. After use the token fields are removed, so the same link can't be used twice.

Secret fields hidden

password and tokens have select: false; toSafeUser() strips them before any response.

Edge cases

SituationResult
Register with an email that is a Google-only account409 with a hint: use Google, or "Forgot password" to set one.
Register again before verifyingAllowed: new name/password, new link. Only the real inbox owner can verify.

Known gap (written in the PRD)

Resetting the password doesn't log out other devices: a JWT stays valid until it expires (7 days). Fix later with a tokenVersion on the user that isAuth checks.

Say it in an interview

"Passwords are hashed with bcrypt at cost 12. Verification and reset links use 32 random bytes; only the SHA-256 hash is stored, links are single-use and expire. I avoid user enumeration with identical messages and a dummy bcrypt compare so timing is the same."

F3Staying logged in (client session)

The JWT cookie is invisible to JavaScript, so how does React know who is logged in? It asks the server once when the app opens.

Three small details that fix real bugs

  1. loading: true at start. Without it, on refresh the user is null for a moment and ProtectedRoute would kick a logged-in user to the login page.
  2. App.jsx does not dispatch null on 401. If that slow response arrived after the user just logged in, it would log them out again (race). It only calls finishLoading().
  3. The 401 interceptor ignores /api/auth/* and current-user. A wrong password (401) is not "session expired". For other calls, a 401 clears the user and ProtectedRoute sends them to login.
client/src/api/axios.js 
const api = axios.create({ baseURL: serverUrl, withCredentials: true });
const IGNORE_401 = ["/api/auth/", "/api/user/current-user"];

api.interceptors.response.use((response) => response, (error) => {
    const url = error.config?.url || "";
    const isSessionExpired = error.response?.status === 401 && !IGNORE_401.some((p) => url.startsWith(p));
    if (isSessionExpired && store.getState().user.userData) store.dispatch(setUserData(null));
    return Promise.reject(error); // the component's catch still runs
});

On the server, GET /api/user/current-user is cached in Redis for 60 s (it runs on every page load). Whenever credits or verification change, the cache key is deleted so the next call is fresh.

ProtectedRoute is only UX

Hiding a page in React is not security — anyone can call the API directly. Real protection is isAuth on the server plus userId in every query.

F4Resume upload and parsing

Optional. The user drops a PDF; the AI extracts skills, projects and an experience summary, which later make the questions personal ("Tell me about the caching in your Drishti project").

Why split it like this

  • PDF → text in the API takes milliseconds and lets a bad file fail immediately with a clear 400. The mimetype is just a label from the browser; the real check is "can pdf-parse read it?".
  • Only text goes to Redis (max 12,000 chars), not a 5 MB PDF — Redis memory is small.
  • Nothing is stored except the AI summary — the PDF and full text are thrown away (privacy, small documents). The summary is saved inside the interview when it starts.
  • The AI's reply is untrusted: resumeAiSchema keeps at most 20 skills and 5 projects and limits string lengths.

F5Starting an interview

The most carefully ordered function in the project: it spends money (credits) and calls an AI that can fail. The order of steps is the whole trick.

Why each step is where it is

  • Reserve first: a double-click sends two requests with the same requestId. Only one insert can succeed (unique index), so the second never reaches the charge step.
  • Charge before AI: don't spend AI money for a user who can't pay.
  • Atomic charge: { credit: { $gte: 50 } } + $inc: -50 in one query; credit can never go negative even with 10 parallel requests.
  • Refund on any failure after charging — and delete the reserve so "Try again" works.
  • The browser keeps the same requestId if the network failed (no answer from server) or the server said INTERVIEW_STARTING; for any other server answer it makes a new one.
server/src/modules/credit/credit.service.js 
export const chargeCredits = async (userId, amount, { interviewId } = {}) => {
    const user = await mongoose.connection.transaction(async (session) => {
        const user = await User.findOneAndUpdate(
            { _id: userId, credit: { $gte: amount } },  // check ...
            { $inc: { credit: -amount } },               // ... and subtract, in ONE operation
            { returnDocument: "after", session },
        );
        if (!user) return null;
        await Transaction.create([{ userId, type: "interview", amount: -amount, balanceAfter: user.credit, interviewId }], { session });
        return user;
    });
    if (user) await clearCache(cacheKeys.user(userId)); // after commit
    return user;
};

Questions are designed for speaking

The questions prompt says: exactly 5, in the order easy, easy, medium, medium, hard; each answerable out loud in its time (no code writing); 1–2 sentences; match the experience level; if a resume is given, base at least 2 questions on the candidate's own projects or skills. The AI returns only the text; the code adds difficulty and timeLimitSec (60/90/120) from QUESTION_PLAN.

Crash in the middle?

If the server dies after charging but before refunding, the interview stays in starting. The cleanup job (every 60 s) finds starting rows older than 10 minutes, refunds them only if the ledger shows a charge and no refund, then deletes them. Running cleanup twice can't refund twice.

Say it in an interview

"Start is idempotent: the client sends a UUID and a unique index on userId + requestId makes a duplicate request return the first interview. Credits are charged with a conditional atomic update inside a MongoDB transaction that also writes a ledger row. If the AI fails after charging, I refund and delete the reserve; a cleanup job covers crashes. A test fires 10 parallel starts with credit for one — exactly one succeeds."

F6Voice: speaking and listening

Voice is hybrid. If the browser can do it well (Chrome, Edge, Safari), the free Web Speech API does it in the browser. If not (Firefox, Brave, Opera…), the browser records / plays audio and our server asks Groq: Whisper turns speech into text and Orpheus turns text into a natural voice. Two hooks hide this — the interview components never know which path ran.

useSpeechSynthesis(gender) — AI speaks

  • speak(text) returns a Promise that resolves when speech ends (or fails — the interview must never get stuck).
  • Picks the best English voice by score: Google/Microsoft/Natural +4, robotic eSpeak variants (name contains "+") −4, gender match +2, en-US/GB/IN +1.
  • isNaturalVoice(best) false → server voice: every sentence is requested in parallel from /api/tts, played one after another (sentence 2 downloads while 1 plays). Blob URLs are cached, so "Repeat question" costs no new request. Any failure → the rest is spoken by the browser voice.
  • Waits up to 1 s for voiceschanged — voices load late, and an empty list must not mean "no good voice".
  • Splits text into sentences (Chrome's Google voices stop after ~15 s), safety timeout for a missing onend, and a run counter so cancel() stops an older speak().

useSpeechRecognition(onFinalText) — user speaks

  • Browser path: continuous + interimResults (grey live text), lang = "en-IN", restart when Chrome stops on silence.
  • Recorder path: MediaRecorder (webm / ogg / mp4 — whatever the browser supports), on stop → /api/transcribe → text added. Silent recordings are not sent (an AnalyserNode watches the volume) because Whisper invents "Thank you." on silence.
  • Auto-switch: a network / service-not-allowed error (Opera, Vivaldi, Linux Chromium, Safari with Siri off) flips to the recorder and is remembered until reload.
  • Both paths: stop() returns a Promise that waits for the last text, so it reaches the answer before submit. Mic denied → "please type".

Real bug: "voice is robotic and my speech isn't written"

On the live site the voice sounded weird and speech wasn't recognised. The console list of voices showed only eSpeak voices → the user was on Firefox on Linux, which has no speech recognition and only robotic voices. In Brave the API exists but Brave blocks Google's speech service, so the mic shows "Listening" and writes nothing. First fix: score voices, speak in sentences, Brave = "please type". Real fix: the browser can't do better, so the server does it — Whisper for listening, Orpheus for speaking — only in those browsers, so Chrome users still cost nothing.

Careful
  • Cost & limits: Groq free tier limits audio too, so separate limiters: voiceLimiter 20/min and ttsLimiter 40/min per user — mic on/off or Repeat doesn't eat the AI answer limit.
  • Privacy: audio is held in RAM (multer memory) and forgotten — never saved.
  • Orpheus terms: must be accepted once in the Groq console, otherwise every call is 400 model_terms_required (and the browser voice is used).
  • Autoplay: audio.play() works because the user already clicked "Start"; if a browser blocks it, play rejects → browser voice.

How to test

  • Firefox / Brave: the question should sound human; DevTools → Network shows POST /api/tts per sentence. Speak, press Mic off → "Converting your voice to text…" → text appears.
  • Chrome: no /api/tts or /api/transcribe calls at all.
  • Tests: server/test/tts.test.js, transcribe.test.js (Groq mocked); client hook tests fake MediaRecorder and HTMLMediaElement.play.
Say it in an interview

"Voice is browser-first: the Web Speech API is free and has zero server load, but Firefox has no speech recognition and Linux browsers only have robotic voices. So I detect capability — not the browser name — and fall back to the server: MediaRecorder plus Groq Whisper for listening, Groq Orpheus for speaking. Both hooks keep the same Promise-based API, so the interview flow just awaits speak() and stop() and never knows which path ran."

Real bug found in testing: "questions.3.answer": null

The first version used { "questions.3.answer": null }. It matched every document. In MongoDB, a numeric path on an array means "index 3" and also "a field called 3 on each element"; that field is missing on every element, and missing counts as null. Fix: check $not: { $type: "string" } and that question exists at that index.

F9Finish and the report

After the 5th answer, the client calls POST /:id/finish. The API only claims and queues; the worker builds the report.

The score is maths, not AI

server/src/modules/interview/interview.service.js 
const calculateScores = (questions, weights) => {
    const averages = Object.fromEntries(CRITERIA.map((key) => {
        const total = questions.reduce((sum, q) => sum + (q.scores?.[key] ?? 0), 0); // unanswered = 0
        return [key, Math.round((total / questions.length) * 10) / 10];        // e.g. 6.4
    }));
    // weighted average (0–10) × 10 → 0–100
    const overallScore = Math.round(CRITERIA.reduce((sum, key) => sum + averages[key] * weights[key], 0) * 10);
    return { averages, overallScore };
};
Worked example (technical mode)

Averages: communication 6.2, content 6.4, technical 6.6, confidence 6.8.
Weighted: 6.2×0.15 + 6.4×0.30 + 6.6×0.45 + 6.8×0.10 = 0.93 + 1.92 + 2.97 + 0.68 = 6.50 → ×10 = 65. This exact case was verified by hand during development.

Retry behaviour of the job

  • The job has 3 attempts (backoff 2 s, 4 s). Between attempts the status stays finishing.
  • Only the last failed attempt puts the interview back to in_progress, so the user can press Finish again.
  • If the job is re-run after a crash and the interview is already completed, it returns at once (idempotent). If the status is something else, it throws UnrecoverableError — no point retrying.
  • The save uses { status: "finishing" } in its filter, so it can't overwrite an interview that moved to another state.

F11History and analytics

/history lists past interviews (9 per page, mode tabs, "Load more") and shows analytics on top: KPI tiles, a score-trend chart, skill bars and the weakest skill.

History: fast pagination

server/src/modules/interview/interview.service.js 
const HISTORY_FIELDS = "role experience mode status creditsUsed report.overallScore createdAt completedAt";

export const getHistory = async (userId, { page, limit, mode }) => {
    const filter = { userId, status: { $ne: "starting" } };  // a reserve is not a real interview
    if (mode) filter.mode = mode;
    const [items, total] = await Promise.all([                // both queries in parallel
        Interview.find(filter).sort({ createdAt: -1 }).skip((page - 1) * limit).limit(limit)
            .select(HISTORY_FIELDS).lean(),                       // light fields, plain objects
        Interview.countDocuments(filter),
    ]);
    return { items, pagination: { page, limit, total, totalPages: Math.ceil(total / limit) } };
};
  • Index { userId: 1, createdAt: -1 } serves both the filter and the sort.
  • Projection: no questions/resume (the heaviest fields) in the list.
  • .lean(): plain objects instead of Mongoose documents — faster, less memory.
  • limit ≤ 50 (zod), so nobody can ask for the whole collection.

Analytics: one aggregation with $facet

Real gotcha

Interview.find({ userId: "abc..." }) works because Mongoose casts the string to an ObjectId. aggregate() does not cast — the $match silently matched 0 documents until new mongoose.Types.ObjectId(userId) was used.

Frontend: the chart (recharts) is in its own lazy chunk (ScoreTrendChart.jsx); analytics are hidden for users with 0 completed interviews and hidden silently if the stats call fails, so the history list still works.

One rule: balance and ledger change together

Every credit change goes through chargeCredits or addCredits, which update the user and insert the ledger row in one MongoDB transaction. A crash in between can't leave a balance without its row. The Redis cache for the user is cleared after the commit — clearing it inside the transaction could let another request re-cache the old balance before the commit.

Why transactions need Atlas / a replica set

MongoDB transactions only work on a replica set. Atlas is one. The tests use MongoMemoryReplSet for the same reason.

The account page shows the ledger newest-first with "Load more" (GET /api/credits/transactions, 10 per page, index { userId, createdAt: -1 }).

Known gap

Users created before the ledger existed have no row for their old credits — their balance is right, the history just starts later.

F13Payments with Razorpay

Plans: Starter 500 credits ₹99 · Pro 1500 ₹249 · Max 4000 ₹599. Two independent paths can confirm a payment — the browser (verify) and Razorpay's server (webhook) — and both must credit exactly once.

server/src/modules/payment/payment.service.js (simplified) 
const fulfillOrder = (orderId, paymentId) => mongoose.connection.transaction(async (session) => {
    const payment = await Payment.findOneAndUpdate(
        { razorpayOrderId: orderId, status: { $ne: "paid" } },          // claim
        { $set: { status: "paid", razorpayPaymentId: paymentId, paidAt: new Date() } },
        { returnDocument: "after", session },
    );
    if (!payment) return { alreadyProcessed: true };
    const user = await User.findOneAndUpdate({ _id: payment.userId }, { $inc: { credit: payment.credits } }, { returnDocument: "after", session });
    await Transaction.create([{ userId: payment.userId, type: "purchase", amount: payment.credits, balanceAfter: user.credit, paymentId }], { session });
    return { alreadyProcessed: false, credit: user.credit };
});

Security checklist

  • Server sets the price — the client sends only planId (zod enum). Otherwise someone could buy 4000 credits for ₹1.
  • HMAC signatures with secrets only Razorpay and our server know; compared with crypto.timingSafeEqual (a normal === stops at the first wrong character, which leaks timing).
  • Webhook uses the raw body — mounted before express.json().
  • Order must belong to the user on verify (else 404); webhook checks amount equals what we asked for.
  • payment.failed only marks created orders as failed, never a paid one.
  • No keys configured → payments return 503 PAYMENTS_DISABLED, the rest of the app works.
Why the webhook matters

The user may pay and close the tab before the browser calls verify. The webhook is Razorpay's server telling ours directly, so credits still arrive. Razorpay retries webhooks, which is why fulfilment must be idempotent.

Why jitter?

If 100 users fail at the same second and all retry after exactly 1 s, they hit the provider together again. A small random extra delay spreads them out.

Real migration story

Lesson: model catalogues change; verify, don't assume.

F15Background queue and cleanup

BullMQ on Redis. Two queues: ai (resume + report) and maintenance (cleanup every 60 s).

Adding a job — with a per-user lock

server/src/lib/queue/aiJobs.js 
export const enqueueAiJob = async (name, userId, data) => {
    if (!isRedisReady()) throw queueDown();                          // 503
    const jobId = randomUUID();
    // NX = only if the key doesn't exist → two parallel requests: only one wins
    const locked = await redis.set(lockKey(userId), jobId, "EX", 300, "NX");
    if (!locked) throw new AppError(429, "You already have an AI task running...", "AI_JOB_RUNNING");
    const reqId = getLogger().bindings?.().reqId;                      // logs of API + worker share an ID
    await aiQueue.add(name, { ...data, userId: String(userId), reqId }, { jobId });
    return jobId;
};

// release only OUR lock — GET + DEL as one atomic Lua script
const RELEASE_LOCK_SCRIPT = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) end return 0`;

Processing a job

  • processAiJob finds the handler by job name, runs it inside a logger that carries jobId, reqId and the attempt number.
  • On success: release the lock, return the result (BullMQ stores it as returnvalue, kept 1 h).
  • On failure: release the lock only on the final attempt. Only our own messages (AppError) reach the user; internal errors become "Something went wrong" (the real error is kept as cause in the logs).
  • GET /api/jobs/:id maps BullMQ's many states to three: pending, completed (+result), failed (+message). Another user's job → 404.

Cleanup job (self-healing)

FindsDoes
starting, not updated for 10 min (max 100 per run)Refund if the ledger has a charge and no refund yet → then delete. Refund before delete: a crash in between is retried safely next minute.
finishing, not updated for 15 minBack to in_progress, so the user can Finish again.

The schedule is created with upsertJobScheduler, so starting several workers still gives one schedule, and the maintenance worker has concurrency 1.

Details that matter in production
  • The worker needs its own Redis connection with maxRetriesPerRequest: null (it blocks waiting for jobs; BullMQ requires this).
  • Redis must use noeviction, or jobs could be silently deleted when memory is full.
  • Graceful shutdown waits up to 25 s for running jobs; unfinished ones become "stalled" and are re-run.

Cache-aside

server/src/lib/cache.js 
export const cached = async (key, ttlSeconds, load) => {
    if (!isRedisReady()) return load();                     // Redis down → just use the DB
    try {
        const hit = await redis.get(key);
        if (hit) return JSON.parse(hit);                      // HIT
    } catch (error) { /* log and fall through */ }
    const value = await load();                             // MISS → DB
    redis.set(key, JSON.stringify(value), "EX", ttlSeconds).catch(...); // no await: don't make the user wait
    return value;
};

Fail open — and why /ready ignores Redis

If Redis goes down, limiters let requests through (passOnStoreError) and the cache reads MongoDB. A broken helper should not take the whole app down. That's also why /ready reports Redis but doesn't fail on it: all servers share one Redis, so failing readiness would mark every server unhealthy at once.

But Redis is required at startup

The rate-limit store loads its Lua scripts when the app starts. If Redis is missing then, the store stays broken forever — so the server refuses to start without Redis (later outages are tolerated). Also only one "Redis down" log line is written, not one per request.

Environment: fail fast

config/env.js validates process.env with zod when the server starts. A missing or wrong value prints a list and exits — much better than crashing on the first user.

Why not z.coerce.boolean()?

z.coerce.boolean() uses JavaScript truthiness: the string "false" is non-empty, so it becomes true. The enum + transform makes "false" really false.

Request validation

server/src/middlewares/validate.js 
const validate = (schemas) => (req, res, next) => {
    for (const part of ["body", "params", "query"]) {
        if (!schemas[part]) continue;
        const result = schemas[part].safeParse(req[part] ?? {});
        if (!result.success) throw new AppError(400, /* "body.email: Enter a valid email; ..." */);
        // Express 5: req.query is a getter → replace with defineProperty
        Object.defineProperty(req, part, { value: result.data, writable: true, enumerable: true, configurable: true });
    }
    next();
};

After validation the controller gets clean data: trimmed, lower-cased emails, numbers instead of strings, unknown fields removed. On the client, getErrorMessage() removes the body.email: prefix before showing the message.

Errors

  • AppError(status, message, code) — our message is safe to show.
  • Any other error → 500 "Internal server error"; the real error goes to the log with the stack.
  • Every error response includes requestId.
  • Status codes used: 400 bad input, 401 not logged in, 402 not enough credits, 403 email not verified, 404 not found / not yours, 409 conflict (already answered, finishing…), 429 limits, 502 email/payment provider, 503 AI/queue busy.

F19Tests, CI and deployment

How the server tests work

  • Vitest + Supertest: real HTTP requests against the Express app (no listen needed — that's why app.js and server.js are separate).
  • MongoMemoryReplSet: a temporary MongoDB in RAM, as a replica set because credits and payments use transactions.

  • AI and email are mocked with vi.mock; tests never read the real .env.
  • Test files run one after another (fileParallelism: false) because they share one DB.
